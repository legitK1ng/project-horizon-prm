# Local-First Architecture & Infinite Scroll Design

## Overview
This document outlines the architecture for migrating Project Horizon's frontend data layer to a local-first model. The goal is to eliminate UI latency when interacting with large datasets (e.g., thousands of contacts or call logs) by reading directly from a local browser database (IndexedDB) and virtualizing the DOM rendering. Supabase will continue to act as the central source of truth, synchronizing data to the client in the background.

## 1. Architecture & Data Flow

### 1.1 Local Database (Dexie.js)
- **Technology:** `dexie` and `dexie-react-hooks`.
- **Structure:** We will instantiate a `Dexie` database instance in `src/lib/db.ts` called `HorizonDB`.
- **Tables:** 
  - `contacts` (indexed by `id`, `last_synced`)
  - `call_records` (indexed by `id`, `contact_id`, `timestamp`)
  - `tasks` (indexed by `id`, `status`, `due_date`)

### 1.2 Eager Sync Engine
- **Initial Load:** On application startup, the sync engine will query Supabase for all records (or records updated since a local `last_synced` timestamp).
- **Background Population:** Data will be upserted into Dexie in chunks to prevent blocking the main thread.
- **Real-Time Subscriptions:** A Supabase realtime listener will be attached to the relevant tables. Any insert, update, or delete event from the cloud (such as an OSINT agent adding metadata) will immediately trigger a corresponding Dexie transaction.

### 1.3 UI Read Path
- The UI will be completely decoupled from Supabase fetch requests.
- Components will utilize `useLiveQuery` from `dexie-react-hooks` to observe Dexie tables.
- Updates to Dexie (via the sync engine) will automatically trigger React re-renders.

## 2. Components & Infinite Scroll (Virtualization)

### 2.1 Virtual Lists
- **Technology:** `@tanstack/react-virtual`
- **Target Components:** `ContactList`, `CallLog`, `ActionsLog`, and potentially specific sections of the Dashboard.
- **Mechanism:** Instead of rendering the full array of items returned by `useLiveQuery`, we will pass the array to the virtualizer. The virtualizer will calculate total height and only render DOM nodes for items currently in the viewport (with a small overscan buffer).

### 2.2 Dynamic Sizing
- Since elements like `CallRecord` cards have dynamic heights based on transcript lengths or generated insights, the virtualizer will be configured for dynamic height measurement (`measureElement` ref on list items).

## 3. Error Handling & Edge Cases

### 3.1 Offline Support
- The app will inherently support offline reads. If the network drops, `useLiveQuery` will continue to serve the last synced data from Dexie.
- (Future Scope) Offline writes will need an outbound queue, but currently, data is primarily generated by backend agents, making offline reading the priority.

### 3.2 Sync Failures
- If the initial Supabase bulk fetch fails, the sync engine will implement an exponential backoff retry mechanism.
- The UI will not show infinite loading spinners during background sync failures; it will display the cached data immediately.

## 4. Implementation Steps

1. Install dependencies: `dexie`, `dexie-react-hooks`, `@tanstack/react-virtual`.
2. Define the Dexie database schema and singleton (`src/lib/db.ts`).
3. Implement the Sync Engine (`src/services/syncService.ts`) with bulk fetch and real-time listeners.
4. Integrate Sync Engine into the application lifecycle (e.g., inside `App.tsx` or a dedicated provider).
5. Refactor `ContactList` and `CallLog` components to use `useLiveQuery` instead of direct Supabase fetches.
6. Wrap the mapped lists in `ContactList` and `CallLog` with `@tanstack/react-virtual` for infinite scrolling.
